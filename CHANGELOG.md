## 2026-08-22 15:52:00 +0800 — A reload brings back every tab's generation, not just Tab 1's

- Status: Uncommitted
- User-facing result: Reloading the page during a video generation no longer presents an idle studio over a machine that is still rendering. The whole tab strip comes back, each tab reclaims the run **it** started with its live progress bar, its model name and an elapsed clock that counts from the original submit rather than restarting at the reload — and when the render lands it lands in that tab's canvas and history. Three tabs rendering means three tabs restored, each polling its own job. It also no longer matters which page you reload on: a studio with unfinished work is mounted at boot, so a run started in the Video studio keeps going even if you reload while looking at History. Cancel now genuinely stops a resumed run instead of only clearing the screen.
- Root cause: three separate holes, all downstream of the same assumption that there is one tab. (1) `StudioTabs` opened with `useState(newTabState)`, so a reload dropped every tab but the first; the jobs of the others stayed in the pending-job registry with no tab left to own them and were never polled again. (2) The resume block took `localPending[0]` — one job, whichever came first — and was gated on `isPrimaryTab`, itself derived from "this tab has no seed", which a reload makes true of *every* restored tab. (3) A studio is loaded on first VISIT, so a reload that landed anywhere other than the studio's own page left its jobs unattended until the user happened to click it. Also on the resume path: no `AbortController` was assigned, so Cancel reset the UI while the poll kept running underneath, and the restored progress card showed no model name because only aspect ratio and duration were carried.
- Fix: The strip is persisted to `sessionStorage` per studio (`saveTabState`/`loadTabState` in `src/lib/studioTabs.js`, validated hard — distinct positive ids, `nextId` past all of them so a later tab can never be handed a live tab's id, and capped at 24 since each entry mounts a studio). Every saved job now carries `tabId` (and `modelName`), and `pendingJobsForTab()` in `pendingJobs.js` decides ownership: a tab resumes its own jobs and only its own, while the primary tab additionally adopts the ORPHANS — jobs whose tab was closed mid-render and jobs saved before tab ids existed — and polls those quietly into History, since there is no canvas of theirs left to restore to. `StudioTabs` now tells each studio its `tabId`, whether it is `primary` (first position, not a seeded copy) and the `openTabIds` it can check an owner against, because the old "no seed = the original tab" test stopped distinguishing anything once a reload restored every tab with a null seed. The video resume was widened from local-only to whichever kind the tab owns, takes an `AbortController` so Cancel stops it, and restores the model name and true submit time. The image studio gets the same per-tab ownership (its jobs are cloud-only) plus the live canvas for its own run, with the timing signature nulled so a resumed job's wall time is not filed as a measurement of the configuration currently on the panels. `App.jsx` consults the pending-job registry at boot and mounts any studio with unfinished work, hidden, so it can resume wherever you landed. The app-instance half of `studioLaneId` moved into `sessionStorage` too: it used to be minted per mount, so a reload moved every restored tab onto a fresh scheduler lane and the next generation would no longer queue behind the run it had just resumed.
- Verification: Frontend node tests 615 ran, 609 pass; the 6 failures are the pre-existing ones at HEAD (5 `hivemindStudioReferences` env failures + `a rejected drop reports WHICH failure it was`), confirmed byte-identical against a stashed baseline. 15 new tests: 7 over strip persistence (round trip, per-studio isolation, junk and empty input, the `nextId` guarantee, duplicate ids, the 24 cap, lane stability) and 8 over resume ownership (a tab claims only its own job, the primary tab takes the orphans and a non-primary tab takes none, junk registries) plus source assertions on the wiring. `vite:build` OK. Live E2E on the fixture dev server (5573) against a fixture control API whose jobs never finish: three tabs generating → reload → all three restored, each with its own progress card, its own model name and elapsed times matching its own submit (0:38 / 0:33 / 0:27), and the fixture log showing three distinct job polls with no double-polling. Reloading onto `page=history` resumed all three anyway (polls in the log, and the card showed 1:24 continuous when Video was opened). Cancel on a resumed run stopped its poll dead in the log. A planted job with a closed tab's id plus a legacy job with none were adopted by Tab 1 as "Resuming 2 pending generations…" without displacing its own live card. With the fixture set to finish, both tabs' resumed runs landed their clip in their own canvas and history and the registry drained to empty. NOT verified: the same flow against a real rented machine (that needs the owner passphrase gate), and the muapi cloud resume path (needs an API key) — those share the code the fixture exercised but were not run end to end. No backend change, so no stack restart is required; the 8765 app serves the rebuilt dist on reload.
- Intended commit message: `fix(studio): a reload restores every tab and the generation it was running`
